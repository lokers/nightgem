# Safety model

[← README](../README.md) · [How it works](how-it-works.md) · [Profile](profile.md) · [Safety model](safety-model.md) · [Troubleshooting](troubleshooting.md) · [OpenCode notes](opencode-notes.md)

nightgem runs an AI agent unattended on your Mac. This page says what stops it from doing damage, and, just as important, what does **not**. For how to report a hole, see [SECURITY.md](../SECURITY.md).

**Assumption.** The model driving a run is well-intentioned but fallible: it can be confused, follow a bad instruction found in a repo or web page, and run a command it should not. The design does not defend against a determined attacker who controls the model and has unlimited time. Read [Residual risks](#residual-risks) before you trust it.

The run never waits on a human and never pushes. Safety is layered so that no single glob has to be perfect.

## Layers

1. **No push capability in the environment.**
   - A fetch-only `GIT_SSH_COMMAND` wrapper (`profile/git-ssh-fetch-only.sh`), an empty `credential.helper`, `GH_TOKEN` / `GITHUB_TOKEN` set to `invalid`, `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=/usr/bin/false`, `GIT_SSH_VARIANT=ssh` and an empty `SSH_AUTH_SOCK`.
   - Push URLs are rewritten with `pushInsteadOf` to a non-existent `nopush://` transport. In 0.1.0 the rewrite is derived from **every remote of every spec repo, on any host** (GitLab, Bitbucket, a self-hosted server, a local path), and an explicit `pushurl` is covered too (git ignores `pushInsteadOf` for a remote that has a `pushurl`, so each pushurl also gets an exact `insteadOf` rule). The rules are computed at every server start, outside the sandbox, from the raw configured URLs. A remote URL or pushurl with a credential in it (`scheme://user:password@host`, or a well-known token as the user name) is a hard `doctor`/`launch` failure that names the repo and the remote and never prints the URL; `doctor` checks every git repo directly under the workspace. The canary checks that every `git remote get-url --push --all <remote>` line of every remote of every spec repo reads `nopush://`. A pushurl that equals (or is a prefix of) a fetch URL, as in a "push to several remotes" setup, cannot be rewritten without also breaking fetch, so a spec repo like that is refused at launch (`doctor` warns, per repo; see [Troubleshooting](troubleshooting.md#doctor-failures)). A user-level `pushInsteadOf` identical to one of ours wins the tie and fails that check, which is intended.
   - **Credentials in a remote URL are refused.** A remote URL that embeds a password or token (`https://<user>:<token>@<host>/…`) would let a push authenticate regardless of the layers above, so `doctor` and `launch` fail on it. Remove the secret from the URL and use a credential helper or ssh outside the run.
   - The sandbox adds the kernel part: `~/.ssh` is unreadable and outbound port 22 is refused, so even a push that got past every other layer has neither a key nor a route. An https push has no credentials to authenticate with.
2. **Unattended permission profile** (`src/profile.ts`). Every rule is `allow` or `deny`, never `ask` (a test asserts this). It denies `git push`, `git stash`, forge and tracker CLIs, other agent runners, `ssh`/`scp`/`rsync`, publishing commands for the common package registries, cloud and cluster CLIs, `question`, `wait_for_user`, tracker tools and watch-mode dev servers (`--watch`, `--watchAll`; `--watch=false` is fine). Edits are allowed only in the task worktrees, the run's spec dir and the run's tmp dir (`<os.tmpdir()>/nightgem-<slug>`, outside the control dir), and never in `SPEC.md`, `RUN.json` or the run config. Your `deny.*` profile fields are added on top. The profile travels in `OPENCODE_CONFIG_CONTENT`, which has the highest precedence and cannot be edited by agents.
3. **Preflight rule check** (`src/rulecheck.ts`). At launch the live `GET /api/agent` rules are checked for any `ask`, and a corpus of probes (`profile/corpus.txt`, plus probes generated from your `deny` fields) is evaluated with OpenCode's free permission evaluator. Launch refuses if a forbidden operation is allowed. See [Preflight canary](#preflight-canary).
4. **Guard plugin** (`profile/guard/`). A text-level defence that runs before every tool call, for the root and every child session. It blocks:
   - `git push` (a standalone `push` token of a git invocation after its global options such as `-C`/`-c`/`--git-dir`, also inside `sh -c` and `eval`; a path or branch that merely contains "push", like `feat/push-x`, is not a push), **every `git stash` form** (`refs/stash` is shared across linked worktrees and trips the stash tripwire) and **network git** (`fetch`, `pull`, `ls-remote`, `remote update`, `submodule update --remote`: the launcher pre-fetched origin);
   - forge and tracker CLIs and package publishing;
   - writes and redirects outside the allowlist, on symlink-resolved paths;
   - commands that reference the run port or password, and `webfetch` prompts (stripped);
   - shell commands (including `sh -c`, `eval`, `$(...)` and backtick strings) and `read`/`grep`/`glob` inputs that reference secret locations: `~/.config/opencode`, `~/.local/share/opencode`, `~/.ssh`, `~/.aws`, `~/.config/gcloud`, `~/.kube`, `~/.docker/config.json`, `~/.netrc`, `~/.npmrc`, `~/.git-credentials`, `~/.config/gh`, tracker CLI logins, `~/Library/Keychains`, the control dir (except the read-only `tool-output` dir), your `deny.secretPaths`, and `.env` files (not `*.example`, `.env.defaults`, `.env.sample`, `.env.template`, `.env.dist`; naming, listing and copying *to* `.env` are fine);
   - environment dumps (`printenv`, bare `env`, `export -p`, bare `set`, ...); plain `env FOO=1 cmd` still works. `sh -c` with a dynamic string and `curl file://` are refused.

   It expands `~`, `$HOME`, `${HOME}`, braces and globs, compares path segments case-insensitively, and does not treat `grep`/`rg` search patterns as paths. **Heredocs:** a quoted delimiter (`<<'EOF'`) makes the body data that is never parsed as shell; an unquoted body counts as data only if it contains no `$(` and no backtick; a body owned by `python3 -`/`node -` is treated as code and gets only a textual backstop check; a body that feeds a shell, `source`, `xargs`, `make` or an unknown program is analysed as shell, and a data body that names a secret location is still refused. **The permission profile globs still apply to the whole command string**, so a heredoc whose text mentions `git push`, `git stash` or `gh` is denied there even though the guard would accept it: for JSONL notes use the `write`/`edit` tool, or neutral wording. After the soft-stop flag the guard blocks `task`/background dispatch **except to the `oracle` agent**, and after a hard stop it blocks every tool.
5. **MCP servers are off.** Every MCP server in your OpenCode config (global `opencode.json`, either the `mcp.<name>` or the `mcp.servers.<name>` layout, plus a config in the workspace) is switched off for the run: the run config overrides each one with an inert, `disabled` stand-in, so the server is never started and cannot hand a run push, PR or tracker access that the shell denies and the guard never see. Only the server names are read, never their commands, URLs, headers or environment. Their `<server>_*` tools are also denied for every agent and listed in slim's `disabled_mcps`, as a backstop.
6. **`sandbox-exec` write boundary** (`src/sandbox.ts`). `opencode serve` runs under a generated profile: `(allow default)(deny file-write*)` with an allowlist for the **workspace root**, the run's temp and data dirs and tool caches. There is no rule for `/private/var/tmp`, `/tmp` or the per-user temp dir, and the canary checks that a write to `/tmp` and to `/private/var/tmp` fails. `TMPDIR` and zsh's `TMPPREFIX` point into the run tmp dir, and a `mktemp` shim (a read-only copy in the control dir, first on `PATH`) makes a bare `mktemp` use it too; the tmp dir is wiped when the server starts. Writes anywhere else, including shell redirects, symlink tricks and scripts, are refused by the kernel. Reads of credential locations the server never needs (`~/.aws`, `~/.config/gcloud`, `~/.kube`, `~/.docker`, `~/.config/gh`, `~/.config/glab-cli`, `~/.config/linear`, `~/.ssh`, `~/Library/Keychains`, `~/.local/share/opencode`, `~/.netrc`, `~/.git-credentials`, your `deny.secretPaths`) are denied too; only `~/.config/opencode` (the server reads it) is not. Outbound connections to the run port and to port 22 are denied for the sandboxed tree, so agents cannot call the run API or reach an ssh git remote. Executing `/bin/launchctl`, `/usr/bin/osascript` and `/usr/bin/crontab` is refused too, because a launchd or cron job would start outside the sandbox.
7. **Auto-reject.** Any `permission.asked` event is rejected over the API and logged as a defect.
8. **Tripwires every 5 minutes.** For every git repo directly under the workspace: HEAD, branch, a hash of `status --porcelain` and the stash count. Plus hashes of the profile, append files and `SPEC.md`. Any violation triggers a hard stop and a "Needs human attention" entry.
9. **Control files outside agent reach.** The password, heartbeat, flags, context snapshot and the launchd plist live in `~/Library/Application Support/nightgem/<slug>/` (mode 0700), outside the sandbox write allowlist.
10. **After the run**, the report verifies that nothing was pushed (`ls-remote`) and records the tripwire results.

**Network git is off during runs.** With `~/.ssh` unreadable and port 22 closed, `git fetch` over ssh cannot work, and the guard refuses network git outright so agents do not burn turns on it. The orchestrator therefore fetches every spec repo's `origin` **before** the server starts (branches are cut from the freshly fetched default branch), and the agent prompts say not to fetch. `git stash` is refused in every form; commit, or write a patch to `$TMPDIR`.

## Preflight canary

Before the first phase the orchestrator runs the rule check and then a canary in three layers. The first two need no model, so they cannot flake:

1. **Guard (in-process).** `decide()` from `profile/guard/decide.mjs` is run over a fixed probe table with the config the plugin builds from `buildGuardEnv`: `git push` in several spellings, `gh`, a write to `/tmp/x`, the OpenCode config and run-dir secrets, `printenv`, the run port, plus the stop flags. Any wrong verdict fails the launch.
2. **Sandbox and env (`POST /api/session/:id/shell`).** The route runs a command in the server's own env and sandbox, as no agent, so the permission rules and the guard do not apply. That makes it a direct probe of the kernel and env layers: `git push` and a `--dry-run` push must fail, every push URL of every spec-repo remote must read `nopush://`, `gh pr list` must fail, a write to `/tmp`, a connect to the run port and a read of a sandbox-denied credential path must fail. A probe that exits 0 fails the launch. Only the probe name and exit code are logged, never output.
3. **LLM (optional, about $0.01).** A small-model session gets an explicit operator-authorized self-test prompt asking it to try four forbidden commands. A probe that succeeds, a `permission.asked` or a cost of $0.05 or more fails the launch. If the model simply declines, it is retried once in a fresh session; if it still proves nothing, a `canary-inconclusive` defect is recorded and the launch goes ahead.

A failure ends the run as `failed` (`preflight-failed`) with the reasons in `RUN.json` defects. See [troubleshooting](troubleshooting.md#preflight-canary-failures) for the individual messages.

## Residual risks

Known limits of the design. They are documented, not hidden, and not treated as vulnerabilities (see [SECURITY.md](../SECURITY.md)).

- **The provider API key in `~/.config/opencode/opencode.json` is not protected by the kernel.** The sandbox blocks writes only, and the server itself must read that file, so the sandbox cannot deny it. The guard refuses shell commands and `read`/`grep`/`glob` input that reference it (and the other secret locations above), but this is a best-effort text and path check, not a boundary. Known remaining bypasses:
  - writing a script and then running it (the script body is never inspected);
  - interpreter code that builds the path at run time, or decodes it first (`base64 -d`, `printf '\x..'`);
  - a decoded or generated `sh -c` string, and any command name or argument produced by a variable that is set in another command;
  - `curl file://` is blocked by pattern, but other local-file readers that take a URL or a spec are not enumerated;
  - **network egress is open**, so anything an agent can read it can also send out.
- **Moving the key to an environment variable is worse, not better.** Agent shells inherit the server's environment, so `echo $KEY` style access is one step away. The run's own `XDG_DATA_HOME` auth store is equally readable by the server and therefore by the sandboxed shell, except for what the guard refuses.
  - **Recommended:** use a dedicated, spend-capped API key for overnight runs. The preflight canary asserts at every launch that the guard blocks reading the OpenCode config, and the launch is refused if it succeeds.
  - **Future hardening (not started):** a `SHELL` wrapper that runs agent shells under a stricter nested `sandbox-exec`. It must first be confirmed that OpenCode spawns shells through `$SHELL`, and that a nested sandbox profile is permitted inside the already sandboxed server tree.
- **Command-name denials are textual.** `gh`, `ssh`, tracker CLIs, `git push`/`stash`/`fetch`... are matched on command words and git argv (including inside `sh -c`, `eval`, `$(...)`, wrappers such as `env`, `nice`, `xargs`, and obfuscation by quoting). A command built at run time (`T=gh; "$T"`), a script that is written and then run, or a git alias already defined in a config file the guard does not read (`-c alias.*` and `git config alias.*` are refused, aliases from `~/.gitconfig` are not) is not caught by the guard. The kernel layers still hold for the dangerous ones: ssh has no key and no port 22, and tracker CLIs cannot read their logins. `git stash` has no kernel layer: a hook that stashes (for example a staged-files lint hook) bumps the stash count and the tripwire then ends the run.
- **Host-control CLIs (`launchctl`, `osascript`, `crontab`) are an escape class.** A launchd or cron entry starts a job OUTSIDE the sandbox and the guard, with your full rights; `osascript` can drive other apps. Three layers close it, each with different blind spots: the **profile** denies plain, post-separator and absolute-path forms; the **guard** matches the names as command words after quote stripping, inside `sh -c`, wrappers, absolute paths and quotes, but textually; the **sandbox** refuses to exec the three binaries at all, which holds whatever the command line looks like. Not covered: another binary that talks to launchd (`open`, `at`) and a program calling the launchd APIs directly. Container, package-manager, orchestration and cloud CLIs are guard-denied by name with no kernel layer.
- **The profile layer cannot be as precise as the guard.** `*git*push*` and `*git*stash*` are globs, so they also deny harmless strings such as `git commit -m "fix push handling"`, or a path containing `push`/`stash`/`gh`. The launcher therefore rejects slugs and task ids that contain the standalone hyphen-separated tokens `push`, `gh`, `ssh` or `stash` (`push-notif` and `fix-stash` are rejected, `pushover` and `stashing` are fine); agents are told to avoid the words or to use `-F file`.
- **bash and `sh` heredocs need a writable working directory.** macOS bash 3.2 (`/bin/bash`, `/bin/sh`) writes the temp file of a here-document to `/private/var/tmp`, and when that is refused (as inside a run, on purpose) falls back to the cwd if the cwd is writable (a rule there would let the sandboxed tree touch the heredoc files of your own bash processes and leave files in a shared dir). Inside a run the cwd is the run dir or a task worktree, so the fallback works; from an unwritable cwd (`cd /`, `cd ~`) a bash or `sh` heredoc fails with `cannot create temp file for here document`. zsh (the agent shell) and `mktemp` are not affected.
- **The tmp dir lives outside the control dir** (`<os.tmpdir()>/nightgem-<slug>`). Anything in tmp is readable and writable by agents, and by other local users the file modes allow.
- **Writes inside the workspace root.** The sandbox allows the whole workspace, so an agent could in principle modify another checkout there. The profile edit rules, the guard and the tripwires detect or block this, but the kernel does not. **The workspace write root also covers nightgem's own checkout if it lives inside the workspace**, so keep nightgem outside the workspace you point runs at.
- **The server password is in the shell environment.** Shell commands inherit `OPENCODE_SERVER_PASSWORD`. The mitigation is the sandbox network deny to the run port and the guard rule on the port, `/api/` and the variable name. Stripping it through a `shell.env` hook is unverified, so a gap remains if the sandbox deny were to fail.
- **`sandbox-exec` is deprecated by Apple.** It works on current macOS, and `doctor` checks that it exists. A future macOS may remove it, and then launches will be refused.
- **Unverified pieces.** The guard's soft-stop flag has not been run end to end (fallback: prompt-only soft stop plus the kill). Interrupting a *running* root session, and background shell processes outliving a session, were not exercised. The process-group kill is the backstop.
- **Budget accuracy is not safety.** The `webfetch` prompt leak and the aborted-stream billing gap make the cost figure an estimate; see [budget accounting](how-it-works.md#budget-accounting).
- **Version coupling.** OpenCode 2.0.29 is the tested version. `doctor` warns on a patch mismatch and fails on a major one. The OpenCode behaviours this relies on are in [opencode-notes.md](opencode-notes.md).

nightgem does not make an unattended AI agent safe to point at a machine that holds data you cannot afford to lose. Use a dedicated, spend-capped API key, keep backups, and read the morning report before you use anything it built.
